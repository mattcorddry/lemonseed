# M9 P1 — LiteLLM as a core platform component

Design for approval. The brief is **as simple as possible**: one stateless container,
one CP-generated config file, one OWUI connection repoint. No database, no portal UI,
no blue/green, no new ports.

## 1. Summary

LiteLLM proxy fronts lemond under the manifest-owned model names. It is a core
component like Postgres and Valkey: supervised by the CP, configured exclusively by a
generated `config.yaml`, reachable only on the appliance. Everything downstream (OWUI,
the OpenAI-compatible endpoint, MCP in P3) consumes LiteLLM; nothing consumes lemond's
model names directly anymore.

## 2. Runtime shape

| Aspect | Decision |
|--------|----------|
| Image | `ghcr.io/berriai/litellm`, **latest stable detected and pinned at build time** (§3) |
| Network | joins `lemon`; publishes `127.0.0.1:<port> → 4000` like every host-facing service |
| Backend | lemond via the existing gateway path: `http://host.docker.internal/_lemonseed/lemond/v1` |
| State | none — config-only mode, no LiteLLM database, no virtual-key store |
| Auth | a CP-generated **master key**, stored `0600` under `/var/lib/lemonseed/litellm/` and set as OWUI's connection API key |
| Lifecycle | CP supervisor: create/start/recreate on config change; **no blue/green** — the proxy is stateless, a failed recreate retries on the next tick |
| Config | `/var/lib/lemonseed/litellm/config.yaml`, regenerated by the CP whenever inputs change; container recreated when the file's hash changes |

lemond stays reachable through the same nginx path OWUI uses today
(`host.docker.internal/_lemonseed/lemond/v1`), so LiteLLM introduces no new host port
and no new exposure.

## 3. Pin strategy (latest stable at build time)

A `litellm` key joins `control-plane/container-images.json`, reusing the existing
deliberate-rebase machinery:

- `scripts/refresh-image-pins.py` gains a **latest-stable resolver**: query the
  `litellm/litellm` GitHub releases (newest non-prerelease, matching D5's channel
  semantics), resolve the tag to an index digest via `docker buildx imagetools
  inspect`, and write `{name, tag, digest}` — exactly what Postgres/Valkey/OWUI pins
  already store.
- Refreshing stays **deliberate** (`make refresh-image-pins` or the per-pin
  invocation), never a silent `docker pull` on deployed boxes; the digest is what an
  appliance actually runs.
- The spike validates the pinned release's config schema (below) and its MCP surface
  (§5) before anything is generated against it.

> **As built (M9 P1):** the pin is resolved — `ghcr.io/berriai/litellm:v1.108.3`
> (1.108 is upstream's LTS line; 1.109/1.110 were rc/dev at spike time), index
> digest recorded in `control-plane/container-images.json`. Detection is
> `scripts/refresh-image-pins.py --latest-stable litellm`: GitHub
> `releases/latest` (fails closed on draft/prerelease), then the registry query.
> The flag is **opt-in** so `--check`, CI and the unit tests never hit the
> network; an explicit `--set-tag` still wins.

## 4. The generated `config.yaml`

The CP renders the file from three inputs: the manifest's model entities, the active
lemond model (from CP settings), and the installed modules' platform-config
contributions (empty in P1; P3 fills it). Shape:

```yaml
# generated by lemonseed-control-plane — do not edit
model_list:
  - model_name: Lemonseed AI
    litellm_params:
      model: openai/<active-lemond-model-id>
      api_base: http://host.docker.internal/_lemonseed/lemond/v1
      api_key: "<lemond api key or 'none', as today>"
  - model_name: Lemonseed AI with Content Filters
    litellm_params:
      model: openai/<active-lemond-model-id>
      api_base: http://host.docker.internal/_lemonseed/lemond/v1
      api_key: "<as above>"
    guardrails: [cf-harmful-child-safety]

guardrails:
  - guardrail_name: cf-harmful-child-safety
    litellm_params:
      guardrail: litellm/cf_harmful_child_safety   # exact id validated by the spike

mcp:
  # appended from installed modules' platform config contributions (P3); empty
  # in P1 — OWUI's static MCP config points here regardless.

litellm_settings:
  master_key: "<CP-generated, also set as OWUI's connection api_key>"
```

Rules:

- **Deterministic and owned**: the file is fully CP-owned; a hand edit is overwritten
  on the next regeneration. Unit tests assert the exact rendering from a given
  manifest + settings + module set.
- **The filtered entity is config-only** — same backend, same params, plus the
  guardrail reference. Changing the active model regenerates and recreates; both
  entities always point at whatever lemond is currently serving.
- **The guardrail id is the one open risk**: the spike confirms
  `litellm/cf_harmful_child_safety` (or its successor) in the pinned release. If the
  built-in set does not exist there, P1 ships with the filtered entity configured but
  the guardrail left to a named follow-up — the entity, mapping and config shape do
  not change.

> **As built (M9 P1) — spike result, all verified against the v1.108.3 source:**
> the id `litellm/cf_harmful_child_safety` **does not exist** (configuring it would
> refuse to boot the proxy). The correct mechanism is the built-in, fully offline
> guardrail **`litellm_content_filter`** with the bundled prebuilt category
> **`harmful_child_safety`**. Two more grounding details the design sketch got
> wrong: the per-model guardrail attach lives **inside** `litellm_params`
> (the router spreads it into the request kwargs), and the master key lives under
> **`general_settings.master_key`** (not `litellm_settings`). The rendered shape:
>
> ```yaml
> # generated by lemonseed-control-plane — do not edit
> model_list:
>   - model_name: Lemonseed AI
>     litellm_params:
>       model: openai/<active-lemond-model-id>
>       api_base: http://host.docker.internal/_lemonseed/lemond/v1
>       api_key: <lemond api key or 'none'>
>   - model_name: Lemonseed AI with Content Filters
>       guardrails: [lemonseed-harmful-child-safety]   # inside litellm_params
> guardrails:                                          # top-level = v2 init
>   - guardrail_name: lemonseed-harmful-child-safety
>     litellm_params:
>       guardrail: litellm_content_filter
>       mode: [pre_call, post_call]
>       default_on: true
>       categories:
>         - category: harmful_child_safety
>           action: BLOCK
>           severity_threshold: medium
> mcp_servers: []          # reserved for P3 module contributions
> general_settings:
>   master_key: <CP-generated>
> ```
>
> Note the failure mode that justifies the probe test below: v2 guardrail init
> **skips** an invalid guardrail with an error log instead of failing the boot —
> so "the filtered entity exists" is not evidence that filtering is enforced.
> The filtered entity is only claimed in a release after the probe test
> (blocked prompt through the entity) passes on real hardware.

## 5. Consumers

- **OWUI:** `openai.api_base_urls` → `http://lemonseed-litellm:4000/v1` (Docker DNS on
  `lemon`; server-side, never browser-facing), connection API key = the master key.
  The CP creates the two model **definitions** that `owui-policy.json` has been
  reserving (now carried under the entity names themselves — "definitions arrive
  with Phase 5"), and per-user visibility maps through OWUI's existing per-user model
  configuration. OWUI's own MCP config points at LiteLLM's `/mcp` endpoint and is
  written once here — P3 modules append to LiteLLM, never to OWUI.
- **Other LAN apps:** the OpenAI-compatible endpoint later (M9 backlog item) —
  nothing to build now beyond the master key already existing.
- **lemond:** keeps its existing name space; its native model name must not appear in
  OWUI's model list once LiteLLM is in place.

> **As built (M9 P1):** the two definitions are **override-style rows** — the id IS
> the LiteLLM entity name and `base_model_id` is null, so OWUI's backend merges the
> row into the connection model in place and the picker carries one entry per entity.
> (A first implementation used workspace-model *wrappers* — separate row ids with
> `base_model_id` → the entity names — and bare-metal review showed every entity
> twice for admins: the OWUI backend adds connection models as base entries
> regardless of the frontend's direct-connection flag, and the picker's dedupe is
> by id, which two look-alikes defeat. Overrides replace them; the retired wrapper
> rows are swept by the reserved-name rule on the first post-upgrade reconcile, and
> a user's saved default model may need one re-pick.) Payloads stay minimal — only
> `id` and `name` are authored (plus the create-required empty `meta`/`params`),
> because every authored field is a permanent drift loop against OWUI's own
> normalization. The rows are not cosmetic: OWUI's model-filtering shows models
> **without** a model row to admins only, so the rows are what makes both entities
> visible to members at all — which is also why they must be override rows: a row
> sharing the base id is merged in place, while a wrapper id would leave the base
> entry standing beside it. Because `models/export` filters `base_model_id != NULL`, observation
> moved to the paginated `models/list` (`owui_client.call` gained query params).
> `evaluation.arena.enable` is pinned off: left on, the OWUI backend appends its
> default "Arena Model" placeholder to every picker. The MCP config
> is **not** written in P1 (deferred to P3 with the first module; the
> `mcp_servers:` section is reserved-empty) — a deviation from "written once
> here", because the MCP mechanics were not validated in the spike.

## 6. Migration, rollback, health

- **Upgrade onto an encrypted M8 box:** the CP generates the config, starts the
  container, then repoints OWUI — chat availability is bounded by the LiteLLM
  container being ready, which the existing ready-gating (chat-ready pattern)
  already expresses. A failure keeps OWUI pointing at lemond until the cutover
  succeeds: repoint last.
- **Rollback (N-1):** the previous slot's CP does not know LiteLLM; it re-owns
  `openai.api_base_urls` and reconciles OWUI back to lemond directly. The LiteLLM
  container keeps running orphaned — harmless, and the next forward update re-adopts
  it. No data, no state, no cleanup needed for correctness.
- **Health:** P1 adds an HTTP-ready check to LiteLLM's status field; P4's live checks
  generalize it. Until then the existing started/reconciled status reporting applies.

> **As built (M9 P1):** the cutover is **atomic and unconditional**. All three
> connection settings resolve from the same context, so they flip together at the
> very first reconcile — a half-cutover (new key on the old lemond URL) is
> structurally impossible. The originally planned readiness gate ("repoint last")
> was dropped for two reasons found in QEMU: (a) with unresolved entries, a box
> that has not chosen a model yet does not keep lemond — it keeps Open WebUI's
> **factory default** connection URL, which is worse than either of ours; and
> (b) after the first successful cutover, a later proxy outage cannot be recovered
> by gating anyway (the stored key is already the master key, so the old lemond
> path is dead regardless). The proxy is owned like every other core service: if
> it cannot start, chat is down and `/api/data` says why. The manifest marks the
> three entries `optional` so a broken litellm *module* degrades to unresolved
> reports instead of a permanently erroring reconcile gate. N-1 rollback is
> unchanged: the previous slot's CP re-owns the connection to lemond directly.
> The reconcile loop re-ticks every supervision pass. LiteLLM **waits** (never
> errors) until a model has been chosen, because there is no model name to front
> before that; the config is re-rendered on every tick and the container is
> recreated only when the hash the running container was started with (persisted
> marker file) stops matching.

## 7. Tests

- Unit: `config.yaml` rendering (model list from the manifest + active model, both
  entities, guardrail wiring on the filtered one only, master-key injection, MCP
  section empty/reserved); pin file entry present and digest-shaped; regeneration
  hash-change detection drives recreate.
- QEMU: both entities appear in OWUI's model list; chat completes through LiteLLM;
  lemond's native name does not leak; stopping the LiteLLM container flips the
  status field (P4 tightens this into a live check).
- BM-1: the same on real hardware, model switching in the panel, per-user filtered
  model mapping.

> **As built (M9 P1):** unit coverage lives in `control-plane/test_litellm.py`
> (exact config bytes for given inputs, guardrail only-when-enabled and only inside
> `litellm_params`, master-key persistence/0600/reuse, hash-driven recreate with a
> persisted applied-hash marker, waiting-not-error before a model is chosen,
> supervisor state machine over mocked docker, pin shape, the policy↔litellm
> entity-name cross-check, and the atomic cutover gate).
> **QEMU scope is deliberately narrower than the plan's line above:** the QEMU
> profile has no GPU and no model, so the proxy stays in its "waiting for a model
> choice" state and is never started (which is also why it needs no image preload
> in the QEMU profile). The QEMU smoke therefore asserts only that `/api/data`
> carries the litellm entry in a defined state; "both entities in OWUI's list",
> "chat through LiteLLM", "no lemond name leak" and the filtered-entity probe
> are **BM-1** items.

## 8. Explicitly out of scope

MCP server registrations and the gateway module (P3), per-module health (P4), the
OpenAI-compatible endpoint toggle and key management for other apps (backlogged),
LiteLLM virtual keys per user, streaming/routing tuning, and LiteLLM's database
mode — permanently out unless a requirement forces it.

> **As built (M9 P1):** the image is preloaded only where it can actually run.
> LiteLLM has **no** `dockerTools.pullImage`/virtio preload in the QEMU profile —
> it only starts once a model is chosen, which the QEMU profile never has, so a
> preload would burn build time and disk for nothing. `make refresh-image-pins`
> accordingly lists no fixed-output hash file for it (rebinding the pin is a
> registry-only operation). Also deferred from this phase per the plan's own gate:
> the OWUI MCP config write (P3) and any portal rendering of the litellm status
> field (P4 generalizes health into live checks).

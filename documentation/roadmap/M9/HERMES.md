# Proposal: Multi-User SSH Sidecar for the Hermes Appliance

**Status:** Draft for discussion

**Date:** 2026-11-16

**Context:** Hermes Agent gateway + profiles run in a single Docker container (no `docker.sock`, no nested Docker). Profiles need execution isolation, background-job support, and predictable per-user resource behavior. Auth proxy handles HTTP access; this proposal covers agent _execution_.

---

## 1. Decision summary

| Decision | Choice | Rationale |

|---|---|---|

| Execution isolation | **SSH sidecar container(s) only** | Real kernel boundary (namespaces, seccomp, dropped caps); supports background jobs; per-user cgroups |

| Bubblewrap backend | **Not used** | Adds a second execution pattern for no gain in this threat model; refuses background jobs (deal-breaker) |

| One container, N Unix users | **Yes** | O(tens of MB) per user, not O(container) per user; uniform ops; matches appliance goal |

| Base image | **Evaluate `mwaeckerlin/hermes:sandbox` first; Debian fallback pre-planned** (see §3) | Leverage existing security work if it fits; don't force it if it assumes 1 user |

| Userdb | **Read-only bind-mounted directory + `/etc/passwd`/`/etc/shadow` symlinks**, generated by script | Live updates without restart; deterministic UIDs; no dynamic PAM/sssd |

| SSH public keys | `**AuthorizedKeysCommand**` wrapping a `curl` to the appliance control plane | No `$HOME/.ssh/authorized_keys` for the agent to read/rewrite; live key rotation |

## 2. Architecture

```
┌─────────────────────────┐        ┌──────────────────────────────┐
│  Main container         │        │  Sidecar container (1)       │
│  (hermes-agent image)   │        │  sshd, N Unix users          │
│  ┌───────────────────┐  │  SSH   │  user alice → home /users/a  │
│  │ multiplexed       │──┼───────▶│  user bob   → home /users/b  │
│  │ gateway + profiles│  │ (key)  │  ...                         │
│  │ per-profile:      │  │        │  per-user: cgroups/rlimits,  │
│  │  terminal.backend │  │        │  private tmp, workspace vol  │
│  │  = ssh            │  │        │  no secrets in image/volumes │
│  └───────────────────┘  │        └──────────────────────────────┘
└─────────────────────────┘
              │
              ▼  (curl, loopback)
        Appliance control plane (profile registry / key distribution)
```

* One sidecar container hosts one Unix user per Hermes profile. `hermes profile create X` → provision sidecar user + keypair + `TERMINAL_SSH_*` in profile `.env`.
* Per-profile isolation is Unix DAC inside one container: users cannot read each other's homes or workspaces (0700, umask 077).
* Background jobs work: the container is long-lived; `terminal(background=true)` runs as designed.
* Per-user resource budgets via cgroups (systemd-in-container) or `pam_limits`, replacing bwrap's per-command rlimits.

### What runs where

| Runs in sidecar | Stays in main container |

|---|---|

| `terminal`, file tools (`read_file`/`write_file`/`patch`/`search_files`), `execute_code` | Gateway, model calls, cron _scheduler_, skills/memory/sessions state |

| Cron job _commands_, subagent shell/file/code actions | `browser_exec` (⚠ runs in main container — disable via `agent.disabled_toolsets` per profile) |

| Any background process the agent starts | Vision/image analysis |

### Known residuals (accepted, documented in appliance docs)

1. **Shared loopback namespace.** User A's dev server on `127.0.0.1:8080` is reachable by user B. Mitigations: appliance guidance steers long-running services to Unix domain sockets (0700 homes make the socket path unreachable cross-user) or gateway-mediated exposure. For work teams needing stronger separation, the escape hatch is tiered sidecars (one container per trust tier), not N containers.
2. `**browser_exec` bypasses the sidecar.** Runs in the main container regardless of terminal backend. Mitigation: `agent.disabled_toolsets: [browser, computer_use]` for profiles that shouldn't have it.
3. **Plugins/hooks/MCP run in the main container.** Out of scope for the sidecar; appliance policy = review-then-ship only curated plugins/skills.
4. **File-sync limits.** Hermes' SSH sync-back has a 2 GiB extraction cap and a hardcoded 120 s bulk-download timeout: keep sandbox-side `~/.hermes` lean; bulk data lives in the workspace volume. Track whether `terminal.ssh_sync_files: false` has landed in our pinned release (pure execution host, no upload/sync-back) and whether we want it on.

## 3. Base image strategy

### Option A (preferred): reuse `mwaeckerlin/hermes:sandbox`

The community project is the closest existing reference: hardened Ubuntu sandbox image (sshd + toolchain), zero secrets inside, key-only login, read-only system files, dropped capabilities, `no-new-privileges`, `pids_limit`, segmented Docker networks, and an **automated isolation test** (plants secret markers everywhere the gateway knows; the real agent searches for them; build fails on first hit).

**Assumption to verify:** the image appears designed for **one sandbox = one SSH user = one bot** (single user `somebody`, single keypair, home = the bot's workspace). If confirmed, it cannot host N users as-is.

* **A1 — multi-container fallback:** run N sandbox containers, one per profile. Rejected for this appliance: N containers was the exact pattern we chose the single-container profile layout to avoid (ops, ports, volumes, keypairs scale with users).
* **A2 — derivative:** build a derived image that adds the multi-user layer on top (multiple `useradd` entries, per-user homes, userdb mounts, quota template). **Feasible only if** upstream's entrypoint/init is user-agnostic (no baked single-UID assumptions, no fixed `HERMES_SANDBOX_SSH_*` single-key bootstrap hard-coded into startup, no root-owned single home baked at build time). Needs an hour of source reading before committing.
* **Decision rule:** if A2's required changes are limited to entrypoint/config surgery (no patching of the security model itself), take A2. If the security properties we want to inherit are intertwined with single-user assumptions, fall back to B.

### Option B (fallback): Debian variant, own hardening

Debian 13-slim + the following hardening checklist. Each item closes a known cross-user leak; "distro default" is **not** sufficient on its own.

1. `**hidepid=2` on `/proc**` — `ps`/`/proc/*/cmdline` expose other users' secrets in command lines. Requires remounting `/proc` at startup (`CAP_SYS_ADMIN` for this container, or `--security-opt` relaxation — acceptable on a secret-less sandbox image). If not achievable, document cmdline leakage as residual and steer agents to config files over secret-bearing CLI flags.
2. **Private `/tmp` per user** (`pam_tmpdir` or per-user tmpfs) — shared `/tmp` is the classic cross-user read.
3. **No sudo/su; strip setuid surface** (`find / -perm -4000`, drop most). Agents use `pip --user`/`uvx`/`npx`/venvs — no system installs is a feature.
4. **Per-user resource budgets** — either `pam_limits` (per-user `RLIMIT_NPROC`/`RLIMIT_AS`/`RLIMIT_CPU`) or, preferred, **systemd as PID 1** with per-user slices (`user@.service`, `DefaultMemoryMax=`/`DefaultCPUQu=` drop-ins). Real cgroups v2 ≈ the OOM isolation that motivated sidecars in the first place. systemd-in-container cost ~15–20 MB.
5. **Yama `ptrace_scope=1**`; verify it survives into the image.
6. `**pam_umask` 077**, homes 0700, per-user workspace volume.
7. **No interactive-shell foot-guns**: keep the standard non-interactive guard at the top of `.bashrc` (agent terminal calls are non-interactive; heavy rc init hangs commands).
8. **Minimal surface**: no daemons on `0.0.0.0`, no image-level cron, no compiler setuid helpers.

Toolchain for agents: ship a _thin_ base (python3, git, openssh-server, GNU tar — **GNU tar is mandatory**: BusyBox `tar` breaks Hermes' skill sync via `tar --no-overwrite-dir`, failing quietly) and let agents self-serve via `npx`/`uvx`/venvs. Anything a profile always needs gets baked into our derived image.

## 4. Userdb: read-only mounted passwd/shadow

**Pattern:** bind-mount a _directory_, not the files.

```
# compose
volumes:
  - ./userdb:/etc/userdb-ro:ro
# inside image (or entrypoint)
ln -sf /etc/userdb-ro/passwd /etc/passwd
ln -sf /etc/userdb-ro/group  /etc/group
ln -sf /etc/userdb-ro/shadow /etc/shadow
```

* **Why a directory + symlinks:** single-file bind mounts freeze the inode. A generator that _replaces_ `/etc/passwd` via rename-and-swap would silently stop being seen by the running container. The symlink path resolves through the mount, so regeneration is **live** — no container restart on user add/delete. (If we must bind files directly, the generator must rewrite **in place** under `flock`, never rename. The directory approach avoids having to remember this.)
* **Locked-password gotcha:** password field must be `"*"`, never `"!"`. sshd treats `!`-prefixed password fields as _account locked_ and rejects **key-based** logins too. We are key-only, so `*` is correct and harmless.
* **Deterministic UIDs are load-bearing:** allocate `UID = 20000 + stable index` from the appliance's profile registry — never hash-derived, never "next free." Workspace volume ownership is keyed to UID; renumbering users flips DAC silently.
* **Source of truth:** the appliance's profile registry (`profile → uid, username, group[, extra groups]`). Generator emits `passwd`/`group`/`shadow` into `userdb/` (mode 0640/0644/0600-ish as appropriate; shadow content is all `*` anyway). `hermes profile create/delete` events drive regeneration; no PAM/sssd dynamic backend is needed.
* **Supplementary groups:** optional `agents` group if we ever want an intentionally-shared directory (default: don't).

## 5. SSH public keys: `AuthorizedKeysCommand`

```
AuthorizedKeysCommand /usr/local/bin/hermes-authorized-keys %u
AuthorizedKeysCommandUser hermes-keys
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
AllowTcpForwarding no
X11Forwarding no
PermitTunnel no
```

Script contract (kept simple — it is on the login hot path and runs as a dedicated low-priv user):

```
#!/bin/sh
# hermes-authorized-keys <username>
# 1. validate <username> against the (read-only) userdb; unknown → fail closed (exit 1)
# 2. serve from cache if fresh (< 5 min); else:
# 3. curl the control plane:  GET /profiles/<username>/public-key
# 4. cache result in /run/hermes-keys-cache/; emit exactly one key line
```

* `%u` is **untrusted input** — no shell interpolation beyond what's shown; fail closed on unknown users.
* **No key material ever lands in `$HOME/.ssh**` — the agent (who owns that home) can never read, clobber, or rewrite the file that grants its own access. Key rotation = update control plane + next login picks it up (cache TTL bounds the wait).
* Cache in `/run` (tmpfs): ephemeral, fast, never persisted.
* Trust model note: we still accept `StrictHostKeyChecking=no`-style gateway→sandbox trust on an internal Docker network (consistent with the community image's stance); the boundary is Docker network segmentation, not SSH host-key verification. If we later want hardening, pin the sidecar's host key at provision time.

## 6. Resource scaling (why one container, N users)

Idle footprint per user is tens of MB, not gigabytes:

| Users | Sidecar idle RAM (est.) | bwrap comparison (not used) | Ops artifacts |

|---|---|---|---|

| 1 | ~30–50 MB | ~0 | 1 container, 1 image |

| 5 | ~150–250 MB | ~0 | same single container |

| 20 | ~0.6–1 GB | ~0 | same single container |

* Containers share the host kernel: 20 sshd users ≠ 20 kernels; base image layers shared → disk does not multiply.
* **Per-user budgets replace per-command limits:** cgroups v2 slices (or limits.d) give the OOM isolation a single shared main container cannot. This is the property we wanted from sidecars in the first place.
* Workload RAM/CPU is user-shaped and budget-capped per user; a runaway agent can't OOM siblings or the gateway.
* If 20+ users ever become real: revisit tiered sidecars (one container per trust tier) — same image, N containers — before reconsidering the architecture.

## 7. Lifecycle integration (appliance wiring)

On `hermes profile create X` (or registry update):

1. Allocate UID from stable mapping; generate ed25519 keypair.
2. Write private key path into profile `.env` (`TERMINAL_SSH_HOST/PORT/USER/KEY`); set `terminal.backend: ssh` + `terminal.cwd` (per-profile workspace path) in profile `config.yaml`.
3. Push pubkey + userdb entry to control plane → generator regenerates userdb (live via symlinks).
4. Per-user quota template applied (cgroup slice or limits.d entry).

On profile delete / key rotate: registry update → regenerate; rotation takes effect at next login (`AuthorizedKeysCommand`).

**Boot order:** appliance gates profile gateway starts on sidecar health so users never see transient SSH errors. Fail-closed behavior on sidecar outage is desired (SSH-backed tools error; they do not silently fall back to the main container's local backend — verify this stays true on our pinned Hermes version).

## 8. Verification plan (do these before shipping)

1. **Canary cross-read test** (from the community project's playbook, adapted): plant marker files in user A's home/workspace; drive user B's agent tools (`read_file`, `search_files`, `terminal`, `execute_code`) to attempt access. Must fail. Run as CI gate on image builds.
2. **Secret-marker hunt:** run the equivalent of `mwaeckerlin/hermes`' isolation test against our image — plant markers anywhere the gateway knows, verify no sandbox-side path exposes them.
3. **Userns not needed:** confirm no bwrap/userns dependency remains (we are not using bwrap — this should be trivially true, but check `hermes doctor` output is clean).
4. **Background jobs E2E:** `terminal(background=true, notify_on_complete=true)` from a profile; verify process survives beyond the tool call and completion notification fires.
5. **Live userdb updates:** add/remove a user via the generator; verify no container restart needed and ownership of existing workspace files is untouched (UID stability).
6. **Key rotation:** rotate a profile key; old key rejected at next login within cache TTL + 1 attempt.
7. **Sync health:** skills sync lands in sandbox (GNU tar present); run a long sync-back once to observe the 120 s/2 GiB limits and size workspaces accordingly; evaluate `terminal.ssh_sync_files` for our release.
8. **Quota enforcement:** fork bomb / memory hog from user A; confirm only A's slice is killed and B + gateway unaffected.

## 9. Open questions

* **A2 feasibility:** does `mwaeckerlin/hermes:sandbox`'s startup assume exactly one user/keypair? (Source read required — decision rule in §3.)
* `**/proc` hidepid inside our Docker runtime:** is the seccomp relaxation acceptable for this one container on the appliance's target hosts? (If the appliance ships as a compose stack we control the answer; on user-managed hosts it varies.)
* **Control-plane endpoint:** does the appliance already expose a profile-registry HTTP API, or do we add a tiny one? (The `AuthorizedKeysCommand` script assumes yes.)
* **Sync policy:** keep default skill/cache sync (needed for file tools on a real remote) or adopt `terminal.ssh_sync_files: false` + explicit workspace mounting if it's stable in our pinned release? Leans: keep default at first, revisit when the opt-out ships.
* **Loopback policy for work-team deployments:** document-and-accept, or default long-running services to Unix sockets in appliance SOUL/guidance templates? (Leans: guidance templates + document.)

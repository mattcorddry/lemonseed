## Backlog: Models & chat UX
- **LiteLLM friendly model names:** stable, friendly models (“Lemonseed AI”, “Lemonseed AI with Content Filters”) fronting lemond, so model name/path changes never churn OWUI model config. The friendly models become the manifest-owned `models` entities (`lemonseed-ai`, `lemonseed-ai-filtered` are already reserved in `owui-policy.json`), replacing the env-era `DEFAULT_MODEL_METADATA`/`DEFAULT_MODEL_PARAMS` approach. Also the cheap path to the OpenAI-compatible endpoint below, and the natural home for group-driven content filtering. **[M9]**
- **Custom model catalog:** friendly display names (e.g. flagged labels), Lemonade `user_models.json` / registry overrides so Open WebUI and Lemonade agree — not alias hacks at load time. **[M9]**
- **Group-attribute editing in the People panel:** the panel lists a group's attributes, and `POST /api/groups/attribute` / `attribute-remove` exist and are gated, but there is **no control that writes one** — an admin has to use the API. The closed `stub.GROUP_ACTIONS` set is the contract; the missing piece is the widget, plus copy that explains what each key does once a consumer exists (next bullet). **[M9]**
- **Group attributes beyond `content_filter`:** the store is built — `group_attributes(group_name, key, value JSONB)` with the key set declared in code as `usermgmt.ATTRIBUTE_KEYS` (D-30), which today holds exactly one key, `content_filter`, and refuses unknown keys rather than storing a typeless blob. Growing the set is a new entry in that dict, not a new schema version. Still open: the **consumers**. Nothing reads `content_filter` yet (it needs the LiteLLM filtered-model item above), and there are no list-valued attributes, so the “append for lists” rule is unimplemented. Note `group_attributes` has **no** `ON DELETE CASCADE` (the additive-only migration guard bans the word), so `usermgmt.delete_group` deletes the attribute and membership rows itself. **[M10]**
- **Re-authentication on group change:** the last-enabled-admin guardrail is built (`usermgmt.set_disabled` refuses self-disable and refuses to disable or demote the only enabled admin; `set_groups` refuses the same demotion), but a group change still does **not** bump `token_generation`, and `verify_session` reads role from the **session record**, not from a fresh `user_groups` query. So demoting an admin leaves their live session — and its `X-Forwarded-Groups` / `X-Forwarded-Role` headers — carrying admin claims until it expires or they sign out. Disabling a user does revoke immediately. **[BL]**
- **MoE vs dense preference by platform:** prefer **MoE** models on low-memory-bandwidth platforms (iGPUs) and dense on high-bandwidth dGPUs when a family has similarly-sized MoE and dense options. Needs a `moe: true` catalog flag + a bandwidth heuristic in `best_fit_model`. **[M9]**
- **GeoIP model preference:** lightweight GeoIP lookup; prefer "local" model families for the user's country (Qwen for China, Gemma for the US) when ranking the default pick. **[BL]**
- **Advanced model tab:** an "advanced" picker tab exposing the full `lemonade list` catalog so power users can pick off-menu models. **[M9]**
- **Catalog models not in the Lemonade catalog:** support models in our catalog that the main Lemonade catalog does not yet offer. Requires a direct HF checkpoint path + `lemonade load` with an explicit checkpoint, plus the llama.cpp arch-support caveat (our pinned llama.cpp must support the architecture). Add a **build-time check** that every catalog `checkpoint` exists in the pinned `server_models.json` — our catalog once disagreed with the registry on a checkpoint's case, which broke the disk-space guard's directory matching. **[M9]**
- **Local Wikipedia cache:** experimental indexed Wikipedia snapshot on spacious, well-connected appliances as an optional knowledge source for OWUI (when native KB tools are re-enabled). **[M10]**
- **More complete user profiles:** full name and address landed with M7 P3 (`users.display_name`, `users.email`, editable through `GET`/`POST /api/profile` and the admin `user.update` action). What is still missing is anything the household would ask for next — an avatar, a per-device or per-room label, a birthday for age-gating — and any of it that becomes a *policy* belongs on a group attribute, not on the user row. **[BL]**
- **Download rate / ETA — needs a lemond API, not a probe.** The old speed-probe is deleted (its URL 404'd, and the ETA never populated). Re-verified against the pinned lemond 11.5.2: model detail carries only `downloaded` / `size` / `checkpoint`, and every candidate progress route 404s, so **no rate or ETA is computable from our side**. Revisit *with* a progress API from upstream. The toolbar **NET** meter below is the mitigation we can build today. **[M9]**
- **Support Omni models:** Omni (`collection.omni`) models are a lemond specific creation, combining
  an LLM, stable diffusion engine, TTS/STT, etc into a single payload. **[M9]**

## Backlog: Open WebUI integration
- **Guard surface expansion:** promote more sections to enforce as portal usage shows what admins actually try to change. All **seven** guards now `enforce` and none is `advertise` (verified in `owui-policy.json`; the People panel shipped, so the `auths/add` guard's "until the portal can create accounts" reason expired — D-17b). Next candidates are OWUI's auth-provider config paths (below). **[BL]**
- **Selective connection management:** let OWUI admins create their own model connections alongside ours (Lemonseed owns its entry, others untouched). Needs per-entry merge semantics on `openai.api_configs`; day one writes the whole set via raw import and enforces exactly one connection. **[BL]**
- **Body-aware request-time guards:** block OWUI-UI writes by request *content* — e.g. reject `POST /api/v1/models/create` when the body's `name` matches `^Lemonseed.*$` — instead of sweeping collisions after the fact at reconcile. Path-only nginx guards cannot see bodies; needs an nginx lua module or a small CP-side validation shim. **[BL]**
- **OWUI's own admin UI is advisory — make it look that way** (merges the retired group-namespace-sync item with the user-panel item): guards fully enforce the CP's ownership (all seven, D-17b), so what remains is cosmetic and copy. OWUI's admin user list is still an editable form that reports success on some fields and fails opaquely on others (`usermgmt.cleanup_owui_accounts` sweeps what it creates behind our back, so the failure mode is confusing rather than dangerous); and OWUI's group editor still *looks* authoritative even though membership is re-derived from `X-Forwarded-Groups` on every sign-in and its edits are not durable. **[BL]**
- **A/B rollback across the M7 auth boundary cannot sign anyone in** — **accepted, must not be shipped silently.** A pre-M7 slot has no bcrypt hash to fall back to (`verify_credentials` is deleted) and no SRP verifier to read, and client-side enrollment means one can never be written for it. So rolling back to a pre-M7 slot locks the portal; the only way back in is a USB reinstall with preserve-user-data plus the “Reset admin credentials” marker, which clears the `admin` group so `/setup` reopens (§13, admin bootstrap). M7 P3 made this **sharper, not softer**: v6 is current, the baseline is v5, and `db.migrate_cp_schema` refuses to migrate anything below the baseline at all, so a pre-M7 database is now formally unsupported rather than merely inconvenient — the forward direction is a reinstall too. With M8's beta install base this is a real support hazard. Either the updater refuses to roll back across an auth-schema boundary, or the schema version is checked before a slot is marked good (see the rollback schema-boundary guard under Modules & infrastructure). **[BL]**
- **SCIM evaluation:** revisit if trusted-header provisioning shows friction. **[BL]**
- **LKG restore as an admin action:** the last-known-good config snapshot today only recovers a *broken* reset. A standalone “restore my settings” endpoint is not built because a reconcile rebuilds everything Lemonseed owns. **[BL]**
- **Config-table snapshot for a failed reset:** before `TRUNCATE TABLE config`, copy the table so a reset that cannot rebuild rolls back byte-for-byte instead of relying on the version-gated LKG snapshot. Add only if reset proves buggy. **[BL]**
- **Manual reconcile button may be unnecessary:** the “Apply Lemonseed settings now” endpoint is the escape hatch for “an admin broke something and wants it back now”. If we never use it, delete it. **[BL]**
- **OWUI auth-provider config is admin-editable:** an admin can add LDAP/OAuth/SCIM config in OWUI's own admin UI (guards do not cover it), and OWUI's OAuth is already half-configured by our trusted-header setup. It cannot actually be used — every OWUI call traverses the Lemonseed session gate — and a settings reset clears it, so day one leaves it alone. Decide whether to guard those paths or keep relying on reset. **[BL]**
- **Web search & retrieval:** self-hosted web search as a module so OWUI KB/web-search tools work without a third-party API key. Needs more research; SearXNG meets the requirements but is often blocked by search engines, limiting its utility. We may need a more advanced Playwright-type search system (check out [kernel.sh](https://www.kernel.sh/docs)). If we cannot find a good self-hosted option, we should streamline connecting to cloud based search & retrieval APIs like Ollama. **[M10]**


## Backlog: Accounts & data lifecycle
- **Directory authentication (choose the layer before building):** LDAP/OAuth/enterprise-directory sign-in for household accounts. Unresolved: OWUI's built-in providers (admin-editable, unguarded, bypasses our portal session + TOTP story), a CP-native directory integration, or host-level PAM/sssd with the CP as the only consumer. Must not weaken the invariant that the nginx `auth_request` gate is the sole login path. **[BL]**
- **Basic SMTP:** the household address already exists (`users.email`, editable by the member themselves at `/api/profile`) and it is **portal-only by decision** — Open WebUI’s identity is always the derived `{username}@localhost` and is never mirrored (D-16′, §3.3), so mail does not need per-account OWUI addresses and probably needs one CP-managed relay credential. Still unbuilt: minimal outbound SMTP for notification mail, and any “we emailed you a reset” flow, which SRP rules out anyway (§9 — the CP can never know or send a password). The service account never needs mail. **[M10]**
- **Tombstoned user deletion (undelete window):** mark a deleted account unusable immediately, then an async worker wipes it across CP + OWUI + pending backups after a ~7-day undo window. Must be evaluated against jurisdictional wipe-within-N-days rules (the tombstone revokes access instantly; data persists during the window). Day one is immediate hard delete. **[BL]**

## Backlog: Portal & platform UX
- **Ownership report as a build artifact, not admin UI:** the config-ownership classification (`owui_portal.build_view`) is developer/agent detail — the portal stopped rendering it after bare-metal review, but the payload is still assembled at request time. Generate it at build time instead so the runtime payload shrinks and the detail cannot creep back into the UI. **[BL]**
- **OpenAI-compatible endpoint toggle:** let an admin expose the appliance as an OpenAI-compatible endpoint for other LAN apps, with simple key management. Two candidate engines: OWUI's own OpenAI-compatible surface, or a CP/LiteLLM-side endpoint in front of lemond (the LiteLLM item makes the latter cheaper). Constraint already decided: `auth.enable_api_keys` is **Lemonseed-managed** (the CP's own key depends on it) while per-user keys stay user-owned, so the toggle must not fight that. The portal's `API` panel is where it belongs; consider a high port that does not traverse the auth layer. **[M9]**
- **Network throughput meter:** a **NET** section in the app toolbar (alongside LOAD + STORAGE) showing Tx/Rx bytes/s over a trailing ~10 s average, with a bar where 100 % = link speed. Read the default-route interface (`ip route get 8.8.8.8`), then sample `/proc/net/dev`. Ethernet first; keep it modular so WiFi can be tuned separately. Expose via `/api/status` telemetry. This is also the substitute for the impossible model-download ETA. **[M10]**
- **Internationalization & accessibility:** multiple languages and dialects, number units, and assistive-technology support (alt text, screen readers). **[BL]**
- **Conduit mobile client:** evaluate [Conduit](https://conduit.mobile/), an open-source Open WebUI client, once the LAN UX is stable (§0). **[BL]**
- **Shared channels & calendar:** household-shared chat channels and a shared calendar as first-party appliance data, not per-user OWUI state. Needs its own data-plane ownership decision (Postgres schema vs module). **[BL]**
- **UX theme support:** multiple preset themes (light, dark, professional, playful). **[BL]**
- **Settings page restructure:** one main "Lemonseed" section for system-wide entities, then one settings box (or tab) per module — Open WebUI as the first module — so a module can contribute parameters and status when installed. **[M9]**
- **Local console menu (still open):** tty4 shows the status splash and tty2 is a root login prompt gated on the Hardware password (M8 P7 removed the autologin); there is no console menu, so power and update actions on the box itself require that shell (§3.7). The portal equivalents landed in M7 P5; the console menu itself remains open. **[BL]**
- **OTP-disclosure copy (D-13):** the People panel promises forced rotation but does not say that the admin who generated a one-time code could sign in as that user until rotation — an accepted cost that the UI has not yet said. **[BL]**
- **Guarded paths answer 403 before the auth gate (T4-A):** nginx `if` + `return` runs in the rewrite phase, before `auth_request`, so an expired admin session on a guarded path sees "managed by Lemonseed" instead of a sign-in prompt; the anonymous-caller fallback is the open item (§3.5 invariant 2). **[BL]**
- **About Lemonseed:** create a page separate from admin settings that is open to all users and shows more info about lemonseed. Not just system status (version, uptime, load graph, etc) but also has a short blurb about what Lemonseed is with a link to https://lemonseed.ai. It should also have an "Open Source Software" section that has logos, 1-sentence descriptions, and links for the major open source technology underneath Lemonseed. It must include Lemonade-Server, llama-server, open-webui, and probably postgres and valkey. Modules' metadata should include open source package descriptions, so we can have an "Open Source Modules" sub-section that can enumerate all installed modules' open source provenance. **[M9]**
- **Fresh and consistent web UI:** The current lemonseed web UI is a very boring and typical LLM-generated CSS. We should work on
  a new UI that embodies our mission and integrates with the OWUI interface (potentially even changing OWUI the CSS in the process).
  We should also develop a simple website at https://lemonseed.ai/ that shares the look and feel of the appliance and provides an overview
  of what we've built, as well as simple documentation and getting started pathway. Since I'm not a UI expert, we might consider
  the new [Hallmark](https://github.com/Nutlope/hallmark) skill if we can leverage it from our Zed environment. **[M10]**

## Backlog: Modules & infrastructure
- **Module catalog specs:** define a Lemonseed **module configuration file** (one file per module in a catalog directory in-tree): execution params (docker-compose fragment / pinned image), UX (logo, name, description, help), and dependencies (Postgres, Valkey, future object store). Catalog entries are what users see and what the CP downloads/sets up. The catalog needs its own **test/release cycle**, and should be hostable on lemonseed.ai/github so new offerings and versions can arrive without a full appliance upgrade. See [MODULES-FRAMEWORK.md](MODULES-FRAMEWORK.md) for more details. **[M9]**
- **Module image pins (strategy):** every Docker module tracks the **newest upstream stable** tag we have validated, pinned explicitly in code so field appliances never float on `:latest`. The build/rebase pipeline bumps the pin, runs unit + QEMU (and hardware when the module is user-facing), then lands it. **[M9]**
- **ComfyUI image generation module:** ComfyUI as a module driven through Open WebUI workflows, VRAM-gated so it never competes with a loaded chat model (see the image-gen row in [DESIGN.md](../DESIGN.md)§0). Need to evaluate `lemond` native image generation / editing capabilities before we prioritize ComfyUI. **[BL]**
- **Live API health:** CP status fields should report **current** health via cheap live checks (`pg_isready` / `SELECT 1`, Valkey PING, HTTP ready) rather than a cached “daemon started once”. If Postgres stops accepting connections after boot, the API must flip to unhealthy. **[M9]**
- **Multi-disk expansion:** additional disks → extra PVs → `vgextend` / `lvextend` / btrfs resize driven by the control plane (§4, §5 storage ownership). **[BL]**
- **Backup / restore:** transactionally clean, space/time-efficient backup including Postgres dump, Valkey dump, and per-module **durable** volumes declared in the module spec. Targets: USB (preflight free-space check; optional encryption) and local SMB/NAS shares. **[BL]**
- **Alternatives to TPM (LUKS key storage):** backlogged fallbacks if the TPM requirement ever proves too rigid: (b) a **web-based boot passphrase workflow** — the box waits pre-mount for an unlock entered through the portal over mDNS; or (c) a **hardware-attribute-derived key** — SHA-256 over static motherboard attributes (eth0 MAC + DMI system serial + boot-device serial), which is enumerable and so protects against casual disk theft only. **[BL]**
- **TOTP / MFA:** see [AUTH-TOTP.md](AUTH-TOTP.md); planned for the `admin` group. **[BL]**
- **TLS on the gateway:** blocked on FQDN/CA UX (M7 D1 — no FQDN, browsers reject self-signed certs and re-block them, a private CA is beyond a home user); revisit alongside directory authentication. The LAN threat model is §9. **[BL]**
- **Build cycle time, residual:** the root cause of the CUDA recompile is fixed (`nixos/modules/artifacts.nix` pins the system closure; mechanism in §8). Still open, in rough value order: (a) stop embedding the version in the hashed toplevel (`metadata.nix` versionFile → tmpfiles `/run/appliance/version`) so a build-counter bump does not force a full `zstd -Xcompression-level 10` re-`mksquashfs` of a ~3.2 GB image — requires deciding how `/run/appliance/version` is delivered out-of-band, so it needs its own design; (b) prune `out/`, which holds 177 GB across 84 `appliance-*` dirs plus a 32 GiB `qemu-userdata.img`, on the **same** filesystem as `/nix`; (c) `scripts/nix-gc.sh --if-needed` is dead at 49 % store usage — separate "always prune stale `out/.build/*` roots" from "collect the store only under space pressure"; (d) `max-jobs = 1` serializes the ~109-derivation plan (a machine-level `nix.conf` choice, not a flake setting); (e) whether `nix-amd-ai` publishes a usable binary cache is **unverified** — and it can never cover `llamaCppCuda`, which is defined in-tree. **[BL]**
- **Cloud service / DynDNS:** remote access + Let's Encrypt; see [CLOUD-SERVICE.md](CLOUD-SERVICE.md). **[BL]**
- **Remote access VPN:** As an interim, enable Tailscale client or similar to allow users to access the Lemonseed appliance securely from anywhere. This allows users to use existing mobile apps (e.g. Conduit) as well. This should be evaluated against the Cloud service design to see whether it's worth building a stopgap or just dive into building the Lemonseed Cloud. **[M10]**
- **Installer stream-to-disk:** partition first, stream SquashFS to `root-a`, avoid multi-GB RAM staging on the live ISO. **[BL]**
- **Rollback schema-boundary guard (CLI):** refuse `lemonseed-update rollback` when the target slot's schema floor is below the live CP database version — a rollback across the M7 auth boundary cannot sign anyone in. Deliberately backlogged: M8 ships rollback without it, and no equivalent check is possible from GRUB. **[BL]**
- **ESP grub.cfg template lag:** the updater refreshes the ESP `grub.cfg` from the **running** system's template (`/usr/share/lemonseed/grub.cfg`), so a template change shipped in release N only reaches the ESP with the apply to N+1 — boot-menu labels lag one release. Fix would be shipping `grub.cfg` inside the release payload (as a payload entry or direct asset) so the apply copies the *incoming* template; touched only when the template changes, so the lag is accepted for now. Immediate refresh on a box: copy `/usr/share/lemonseed/grub.cfg` over the ESP's `grub/grub.cfg`. **[BL]**
- **QEMU testing harness for the USB installer:** drive `lemonseed-installer.iso` under QEMU/OVMF end to end — boot the ISO, run the web installer against a virtual disk (including the TPM/disk-encryption path via `swtpm`: format, `cryptenroll`, reboot, silent token unlock) — then assert the installed appliance comes up healthy. Would make the installer→boot path and the P7 cryptenroll/cryptsetup chain release-testable without bare metal. **[BL]**
- **Hermes Agents:** Add a module for hermes agents. We will need to either: (a) run a Docker container for each user on our system, or (b) use [Hermes Multiplexing](https://hermes-agent.nousresearch.com/docs/user-guide/multi-profile-gateways#alternative-one-gateway-for-all-profiles-multiplexing).  In the (a) case, we should do lazy activation; only launch a Hermes agent when a user activates it via the web UI module page. Once it has been activated once for the user, it should stay running (even after reboots) until the user deactivates it, since Hermes is designed for background / always-on work. Hermes should be preconfigured for our LLM as well as our MCP, and we should think about what storage systems it can access. **[M10]**

## Backlog: Other
- **Validate the AMD dGPU path on real hardware:** the Vulkan backend, `select_backend` dispatch
  and `hardware.py` AMD discovery all handle a PCIe Radeon, but no discrete AMD card has ever
  been booted on the appliance — Strix Halo APUs are validated, dGPUs are not. One bare-metal
  tier-D run on a dGPU box closes it. Candidate hardware already exists (a Navi 33 / Radeon RX
  7600, `1002:7480`, currently a PCI device on the dev host at `01:00.0`, not in an appliance).
  Note the semantic difference the APU tests cannot cover: an APU's model budget comes from the
  `ttm.pages_limit` carve-out of system RAM, a dGPU's from its own VRAM, so the planner's
  fit-versus-memory arithmetic is a different path, not the same one with different numbers.
  Fold into the next bare-metal cycle. **[M9]**
- **AMD ROCm/HRX backend, NPU (XDNA):** Enable the more advanced ROCm LLM engine for AMD GPUs and NPUs, perform A/B performance testing versus Vulkan. **[BL]**
- **Heterogeneous GPU planner:** Enable multiple GPUs, potentially of different sizes, speeds, or manufacturers. Ideal state is that these GPUs can participate in a single LLM; fallback is that they must be partitioned into various uses (e.g. LLM, Stable Diffusion, Speech). **[BL]**
- **ARM builds:** Support for the ARM CPU and NEON GPU platform. **[BL]**
- **Secure Boot:** Load kernel certificates into the TPM root of trust, enable secure boot where hardware support exists for it. **[BL]**
- **Revisit whether we want to store the clear text hardware password on Lemonseed:** the P7 design stores it in `cp_meta` so an admin can read it in Settings → Advanced, but every other consumer works from hashes alone (LUKS slot 0 passphrase, TPM token, `/etc/shadow`, GRUB PBKDF2). Dropping the plaintext only costs the reveal — decide whether the convenience is worth the stored secret. **[BL]**
- **Offline installs:** Support for the full startup payload (LLM model, container images, etc) on the USB stick, enabling offline installation without an internet connection. Useful for larger volume installs. **[BL]**
- **VGA console boot experience:** (Low priority) Improve the UI for users who have a KVM attached to the appliance: enable an EFI boot
  splash screen with our logo and color scheme, overlaying status messages into a "status box" in the lower half of the page. This should
  include boot progress during bootup, hostname & IP in normal operations, and setup progress during USB setup. **[BL]**
- **Hardware diagnostics boot option:** Provide some kind of hardware diagnostic boot target at the GRUB menu; this could be as simple
  as memtest86+, or it could be something that boots into a real Linux kernel and runs more expansive hardware tests. Useful for users
  who are experiencing hardware instability problems. GPU health tests would be amazing if possible. **[BL]**
